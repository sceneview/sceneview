- **Disposing a scene is much less likely to block the main thread on the GPU backend ([#4828](https://github.com/sceneview/sceneview/pull/4828)).** Deferred releases (`destroyRenderer`, the engine, a cancelled async model load) waited for a fence created when they were deferred, then ran a Filament release that waits for everything queued since: on a shared engine, the next screen's shader compilations, an ANR from the main looper. They now wait until a fence is found reached at most 48 ms after it was created, so the release only waits for what the main thread queued in those 48 ms; a shader compilation queued in that window is still waited for. When the main thread polls less often than every 48 ms, no fence counts as fresh and the release falls back to running 5 s after its first check, the engine's own destroy included; that fallback still waits for a shader compilation queued just before it fires (about 2 s with the 2 s of shaders measured, 66–300 ms polls), so it bounds how long a release is held back, not how long it can block. If the main looper is quitting, the release runs at once instead of being lost. The engine is also built with `engine.frame_info.disable_gpu_complete_metric`, so `destroyRenderer` no longer joins a thread parked in an unbounded GPU fence wait, and `VideoNode.destroy()` releases its external texture through the same deferral instead of draining it synchronously.
