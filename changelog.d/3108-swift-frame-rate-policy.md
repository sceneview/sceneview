- **iOS / macOS / visionOS: `FrameRatePolicy`, the Swift half of on-demand rendering ([#3108](https://github.com/sceneview/sceneview/issues/3108)).** `SceneView { … }.frameRatePolicy(.onDemand())` — the default — parks SceneViewSwift's own per-frame driver once nothing is moving, and invalidates the `CADisplayLink` it runs on so no display cadence is requested while the scene is idle; `.continuous()` never parks. Same case names, same `maxFps`, same default as the Android `FrameRatePolicy` in this release, with `SceneRenderInvalidator` + `.renderInvalidator(_:)` as the counterpart of `rememberRenderInvalidator()`. **The guarantee is not the same, and the docs say so in a table rather than in a footnote:** Android owns the Filament render loop, so `OnDemand` there means no GPU frame is produced, whereas `SceneView` on Apple is a SwiftUI `RealityView` and RealityKit owns its loop — no public gate, no `isPaused`, no `setNeedsDisplay`, no cadence option on `ARView.RenderOptions` — so `.onDemand` **cannot** stop it presenting. What it saves on iOS is SceneViewSwift's CPU and the cadence request, not the GPU. Three further divergences are documented rather than papered over: `maxFps <= 0` is clamped to `1` where Kotlin throws (a Swift `enum` case has no failable construction point, and trapping inside a display-link callback would turn a caller's typo into a shipped crash); `requestRender()` is a cadence hint on iOS, not the thing that makes a frame happen; and macOS gets the parking and the cap but **no** cadence request at all, because `CADisplayLink.init(target:selector:)` is unavailable there and a SwiftUI `RealityView` vends no `NSView`/`NSWindow`/`NSScreen` to obtain one from. Going above 60 Hz on a ProMotion **iPhone** additionally needs `CADisableMinimumFrameDurationOnPhone` in the host app's `Info.plist` — a framework cannot set it for its host — and that path is flagged **unverified** in the DocC, the guide and the migration note: it was developed without a ProMotion device and the Simulator cannot exceed its host's refresh rate.

- **iOS / macOS / visionOS: the turntable and the release coast no longer judder against RealityKit's presentation ([#3108](https://github.com/sceneview/sceneview/issues/3108)).** `SceneView`'s camera-motion loop ticked on a hard-coded `Task.sleep(nanoseconds: 16_666_667)` — 60 Hz written into the source on a platform that ships 120 Hz phones — and `Task.sleep` guarantees a minimum delay, never a phase, so the camera pose was recomputed off-beat from the frames RealityKit was actually presenting. The loop now ticks on a `CADisplayLink` (`Task.sleep` remains the macOS fallback, where no display link is reachable). Motion already integrated against elapsed time, so `autoRotate(speed:)` values and inertia tuning are unchanged — what changes is the smoothness. **What is established here is the tick source, not the visual result:** the change was written and unit-tested without an on-screen comparison, so the judder is fixed at its documented cause (an unphased 60 Hz timer driving a camera whose frames are presented on vsync) rather than confirmed gone by observation. A before/after on a real display, and especially on a ProMotion iPhone, is still owed.
